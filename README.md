# HelioOps

Space-weather storm pipeline: detect a CME from coronagraph imagery, predict sector
impact, generate operator advisories, verify them.

```
backend/     FastAPI monolith — all four layers
deployment/  Dockerfiles, compose, Supabase schema
frontend/    Next.js dashboard
```

## Run it

```bash
pip install -r backend/requirements-dev.txt      # drop -dev for serving only
cp .env.example .env                             # set GROQ_API_KEY
PYTHONPATH=. uvicorn backend.app:app --reload    # API on :8000

cd frontend && npm ci --legacy-peer-deps && npm run dev   # UI on :3000
```

Whole stack in containers:

```bash
docker compose -f deployment/docker-compose.yml up --build
```

## Verify

```bash
PYTHONPATH=. pytest backend/tests -q
PYTHONPATH=. ruff check backend/ --ignore=E501,F403,E402
curl -X POST localhost:8000/api/detect/2024-10-G4
```

## The pipeline

```
backend/cv        data_ingestion -> image_threshold_algorithm -> storm_event_generator
backend/ml        LightGBM quantile regression -> GPS error + HF blackout, with 95% CI
backend/genai     RAG over NOAA/ICAO/NERC/IMO docs -> per-industry advisory -> verifier
backend/adapters  the seam; backend/pipeline.py talks to these, never to the layers
```

`POST /api/detect/{storm_id}` runs all four. `WS /ws/stream` streams the same run
stage by stage. Storm ids: `2024-10-G4`, `2024-05-G5`.

Every stage falls back rather than failing: no cached frames -> stub StormEvent,
no checkpoints -> conservative predictions, no advisory -> escalate-to-specialist.

## Offline pipelines

Not needed to serve; they produce what `backend/data` and `backend/ml/checkpoints`
already contain.

```bash
PYTHONPATH=. python -m backend.cv.data_ingestion.cache_fits --storm 2024-10-G4
PYTHONPATH=. python -m backend.cv.image_threshold_algorithm.preprocessing --storm 2024-10-G4
PYTHONPATH=. python -m backend.embeddings.ingest_aviation

# ML layer, in order. Trains on synthetic data only -- see the note below.
PYTHONPATH=. python backend/ml/01_data_generation_eda.py   # -> data/synthetic_storms.csv + eda_plots/
PYTHONPATH=. python backend/ml/02_train_and_tune.py        # -> the 6 checkpoints
PYTHONPATH=. python backend/ml/03_anchor_test.py           # physics gate; exits non-zero on failure
```

### On the ML training data

The 6 quantile checkpoints are trained on **synthetic** storms generated by
`01_data_generation_eda.py` from hand-written, physics-shaped rules (4,800 rows,
120 storms x 40 frames, seed 42, committed). The reported R2 and pinball loss
measure how well LightGBM recovers those rules -- not how well it forecasts real
space weather. Quote them that way.

What that does buy: calibrated intervals (95% PICP measured at 95.9% GPS /
94.2% HF) and the correct severity ordering, which `03_anchor_test.py` gates on
a G5 anchor and a quiet baseline.

## Deploying

The backend is one stateless container — a single FastAPI process, no queue, no
worker, no second service — that reads `backend/data` from the image. It runs
as-is on Hugging Face Spaces (the root `Dockerfile`, see
[`docs/HOW_TO_DEPLOY_BACKEND.md`](docs/HOW_TO_DEPLOY_BACKEND.md)), Cloud Run, Fly,
or Render with scale-to-zero. Point the frontend at it with `VITE_API_URL`
**at build time** (it is inlined into the bundle).

Cold start is dominated by loading the BGE embedder and ChromaDB (~10-20s). If
scale-to-zero cold starts matter more than idle cost, keep one warm instance.

# 7 — What went wrong the first time

*The honest chapter. The first version shipped green, tested, verified live —
and with its headline capability unreachable.*

---

## 7.1 The claim, and the reality

Commit `2ea377a` shipped at 16:06 with a confident message:

> Backend — `GET /api/preflight/{storm_id}` (new `backend/preflight.py`, ~300
> lines): predicts which fallbacks will fire, runs **four cross-source physics
> conflict rules** using the same parsers the real run uses...
> Verified: 270 backend tests pass (25 new), ruff clean, frontend test + build
> pass, and live uvicorn returns correct results for both storms.

Everything in that paragraph is true. The tests passed. The endpoint worked. The
panel rendered.

And on a fresh clone of the repository, **not one of the four conflict rules
could ever fire.**

## 7.2 Why

Every cross-source rule needed at least two of the DONKI, flare and L1 caches.
None of those caches were committed. They are generated by prefetch scripts and
sat in each developer's working copy, ignored by git.

So the code path was:

```
cache file does not exist
  -> emit "cache missing" (info)
  -> leave the parsed value as None
  -> every conflict rule guarded by `if cme and l1:` is skipped
```

A fresh clone returned the same four "cache missing" findings, for both storms,
forever. The panel worked perfectly and said nothing.

## 7.3 Why the tests did not catch it

Twenty-five tests passed, including a full class covering the conflict rules:

```python
class TestConflictRules:
    def test_l1_faster_than_launch_fires(self): ...
    def test_l1_below_drag_floor_fires(self): ...
    def test_northward_bz_with_strong_g_fires(self): ...
```

Every one of them called `_conflict_findings()` directly with **fabricated
dictionaries**. They proved the rules *computed correctly given inputs*. Nothing
proved the inputs ever arrived.

This is the classic test-shaped blind spot, and it is worth naming precisely
because it is so easy to reproduce:

> Unit tests verify a function against inputs you supply. They cannot verify
> that anything supplies those inputs in production. A function tested only
> against fabricated inputs is tested as a calculator, not as a feature.

The missing test is an integration one, and it is embarrassingly simple in
hindsight: *run the real check against the real repository and assert that the
two storms produce different findings.* Chapter 9 covers what was added.

## 7.4 The root cause, found while fixing it

The obvious fix — commit the caches — turned out to be impossible for two of the
three, and finding out why explained a second, older mystery.

**NOAA's `rtsw` (solar wind) and `xrays` (GOES flux) endpoints are real-time
only. They take no date parameter.**

You cannot ask them for October 2024. You can only ask them for *now*. So
`backend/data/cached/l1/2024-10-10.json` does not contain October 2024 data. It
contains whatever was current on the day someone ran the prefetch script. The
filename is a label, not a description.

Committing those files would have shipped 8 MB of data that the check could only
ever report as unusable.

**And it explained something nobody had connected.** The flare classifier had
been reporting C-class — that is R0, no radio blackout — for two storms that
were X-class events. The classifier was not broken. It searches for the peak
flux within ±6h of the storm timestamp, and *nothing in the file falls inside
that window*, because the file is from a different month. The peak search finds
nothing and correctly reports nothing.

A pre-existing wrong number, sitting in plain sight, explained as a side effect
of investigating a different bug.

## 7.5 What the fix actually did

Commit `a18490b`, 47 minutes later. Six changes:

**1. Commit the DONKI caches.** DONKI is the one source that serves historical
dates — 44 KB, 20 and 24 real 2024 records. That makes stub-vs-DONKI the
comparison that can run on a clean checkout, and it introduced the new
`stub_donki_speed_mismatch` rule:

| Storm | Reference | DONKI | Drift | Result |
|---|---|---|---|---|
| 2024-10-G4 | 1480 km/s | 1323 km/s | 11.9% | silent |
| 2024-05-G5 | 2200 km/s | 1332 km/s | 65.2% | **fires** |

The commit message states the point plainly: *"The two storms now differ, which
is what stops the panel reading as a cookie banner."*

**2. New `*_cache_stale_epoch` rules.** Catch the wrong-epoch trap explicitly
and withhold those sources from the physics rules, so a date-range error is
never reported as two instruments disagreeing. `l1/` and `xrs/` gitignored, with
the reasoning and the regeneration commands in the ignore file itself.

**3. Demote conflicts under stub replay.** `detect()` returns the stub at
`detect.py:133` before reading any of these sources, so a disagreement between
them cannot change the output. Findings drop `warn` → `info` and explain why.

**4. Fix the false "never writes" docstring** — and the behaviour behind it.
TTL cache plus lifespan warm-up; 9.7s → 0.31s. Covered in
[chapter 6](06-the-read-only-invariants.md#65-the-fourth-one-admitting-what-is-not-read-only).

**5. Rebuild the progressive disclosure.** Layer one becomes a plain-English
headline from the most severe finding instead of a count of warnings. One button
label replaces Run / Run anyway.

**6. Extract `gateDecision()`** into `frontend/src/preflight.js` and assert it in
the node runner the repo already had — no vitest, no jsdom added.

Tests went from 25 to 35 in `test_preflight.py`, and 270 to 284 overall.

## 7.6 The three lessons

**A feature is not shipped until it can fire on a clean checkout.** "It works on
my machine" had a specific mechanism here: uncommitted data files. The test for
this is not clever — clone the repo somewhere else and look at the output.

**Passing tests can measure the wrong thing.** Twenty-five green tests
described a calculator that was correct and unreachable. Ask of any test suite:
*does anything here prove the code runs in production, or only that it computes
correctly when called?*

**A comment that overstates a guarantee is a liability.** "Never writes" was
load-bearing documentation that was false. The fix was not just to make it true
— it was to scope the claim precisely enough that it stays true, and to say
which part is *not* covered.

## 7.7 Why this chapter exists

It would be easy to document the current state and never mention the first
version. The commits are public; anyone can `git log`. But more to the point, a
judge who asks *"how do you know your checks actually run?"* deserves the real
answer, which is: **we did not, for 47 minutes, and here is what we changed to
find out.**

The failure is also the strongest evidence that the review was real. A feature
that ships and is never revisited has been written, not evaluated.
